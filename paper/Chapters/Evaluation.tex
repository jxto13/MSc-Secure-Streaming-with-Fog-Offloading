\chapter{Evaluation}
\label{Evaluation}

\quad This chapter evaluates the proposed livestreaming framework by testing the implemented system under controlled and realistic network conditions, the goal is to collect quantitative data that demonstrates how the architecture performs, building on the design and mechanisms described in \textbf{\Cref{Design and Implementation}}.

\quad The analysis begins by outlining the experimental setup, including hardware platforms, network configurations, and test scenarios. Because of limited physical equipment, part of the evaluation relies on simulated tests that reproduce large-scale conditions, and the other ia a real-world experiment is conducted using the Android implementation from \textbf{\Cref{sec:android frontend}} to confirm the feasibility of client offloading in practice.


\section{Evaluation Environment}
\label{sec:evaluation environment}

\quad The evaluation was conducted inside a containerized environment designed for reproducibility and scalability, where the streaming server, Restreamer, multiple client replicas, and the monitoring stack each ran inside Docker containers connected to a shared bridge network \textbf{\Cref{fig:deployment}}, deployed on a \textbf{Razer Blade 15 Advanced Model (Mid 2021)} equipped with an Intel i7-11800H CPU (16 threads, up to 4.6,GHz), an NVIDIA RTX 3070 Mobile GPU, 64GB of RAM, and running Manjaro Linux with kernel version 6.6.99.

\begin{figure}[H]
	\centering
	\includegraphics[width=0.95\textwidth]{Evaluation/system.png}
	\caption{Containerized deployment of server, clients, and monitoring stack.}
	\label{fig:deployment}
\end{figure}


The roles of these components within the environment can be described as follows:

\begin{itemize}
	\item \textbf{Restreamer} ingested a live video source and re-encoded it into a format suitable for multicast delivery. This ensured a consistent input stream across experiments and isolated results from variability in video input.  
	
	\begin{figure}[H]
		\centering
		\includegraphics[width=0.95\textwidth]{Evaluation/restreamer.png}
		\caption{Restreamer interface providing the test video source for the evaluation.}
		\label{fig:restreamer}
	\end{figure}
	
	\item \textbf{tcgui} configured packet loss on the host-side \texttt{vethXXX} interfaces of the client containers. A Bash script automated this by scanning for containers with the prefix \texttt{iris-client-*}, mapping each client’s \texttt{eth0} to its paired veth device, assigning a random packet loss rate, and posting the configuration to the \texttt{tcgui} HTTP API. This ensured that every client container experienced a reproducible but randomized loss pattern at its ingress interface, \textbf{\Cref{fig:tcgui}} illustrates the \texttt{tcgui} interface for manual rule application, while \textbf{\Cref{alg:packet loss script}} presents the automation script.
	
	
	\begin{figure}[H]
		\centering
		\includegraphics[width=0.80\textwidth]{Evaluation/tcgui.png}
		\caption{tcgui interface for configuring delay, jitter, and packet loss on client veth interfaces.}
		\label{fig:tcgui}
	\end{figure}
	
	
	\item \textbf{Prometheus} operated by periodically scraping data from an exporter embedded in the streaming server, storing the collected time series in its database for retrieval and analysis.
	
	\item \textbf{Grafana} connected to Prometheus and provided interactive dashboards to visualize these server-side metrics in real time and to archive them for later analysis. Dashboards tracked bandwidth usage, retransmission activity, and playback stability across all experiments.  
\end{itemize}

\section{Discussion}

%Three insights emerge from the data. First, static FEC increased overhead without improving reliability, often worsening playback continuity. Second, retransmissions alone provided the best trade-off, reducing packet loss to below 2\% with moderate bandwidth. Third, reinforcement learning improved efficiency compared to fixed FEC when retransmissions were enabled, but it did not outperform the retransmissions-only case.  

%Unicast dominated retransmission traffic, with multicast contributing less than 17\%, suggesting that further tuning of coding and multicast selection thresholds could yield stronger gains.


\quad The results reveal several insights. First, static FEC consumed substantial bandwidth without improving reliability, often worsening playback continuity. Second, retransmission alone provided the most efficient trade-off, cutting packet loss below 2\% and halving missed deadlines with only marginal overhead. Third, reinforcement learning improved efficiency compared to static FEC, but it did not outperform the retransmissions-only case.  

\quad Most importantly, the real-world evaluation confirmed that fog offloading was both functional and beneficial. In the \texttt{RL\_ret\_on-fog\_on} scenario, missed deadlines dropped to just 1915, an 80\% reduction compared to the \texttt{RL\_baseline}, while overhead remained nearly identical at 20.1\%. This demonstrates that offloading improved timeliness and playback stability without the steep bandwidth penalties seen in AI-driven or FEC-heavy configurations. The results validate the design goal of leveraging nearby devices and fog resources to enhance performance under realistic conditions.  

\quad Unicast dominated retransmission traffic, with multicast contributing less than 17\%, suggesting that further tuning of coding thresholds could yield additional efficiency gains.

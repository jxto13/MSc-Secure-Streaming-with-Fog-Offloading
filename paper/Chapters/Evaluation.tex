\chapter{Evaluation}
\label{Evaluation}

\quad This chapter evaluates the proposed livestreaming framework by testing the implemented system under controlled and realistic network conditions, the goal is to collect quantitative data that demonstrates how the architecture performs, building on the design and mechanisms described in \textbf{\Cref{Design and Implementation}}.

\quad The analysis begins by outlining the experimental setup, including hardware platforms, network configurations, and test scenarios, it then presents results from core modules such as the adaptive redundancy strategies introduced in \textbf{\Cref{sec:reinforcement learning}}, the retransmission scheduling framework in \textbf{\Cref{sec:network scheduler framework}}, and the peer-assisted recovery mechanisms from \textbf{\Cref{sec:mesh networking}}. Further experiments use the Android frontend from \textbf{\Cref{sec:android frontend}} to verify offloading performance in practical deployments.

%\quad The evaluation uses a containerized deployment to ensure reproducibility and employs a monitoring stack for continuous observation of system behavior. Network impairments such as loss and latency are introduced in a controlled manner, allowing wireless conditions to be simulated accurately. This method ensures that performance measurements remain representative of real-world usage while retaining repeatability.


\section{Evaluation Environment}
\label{sec:evaluation environment}

%\quad The experimental environment is built from three core technologies. Docker is used to deploy both the server and client components, allowing reproducible configurations and enabling scalability to dozens of concurrent receivers per host. Containers run isolated instances of the protocol while maintaining shared networking interfaces, which simplifies large-scale experimentation.

%\quad Monitoring and metrics collection rely on Prometheus and Grafana. Prometheus scrapes the exposed metrics from server and client containers, including throughput, retransmission counts, buffer occupancy, and end-to-end latency. Grafana dashboards visualize these metrics in real time and provide a time-series archive that supports post-experiment analysis. This monitoring stack ensures that all relevant measurements can be observed without interfering with the operation of the streaming pipeline.

%\quad To simulate wireless network conditions, the Linux traffic control tool (\texttt{tc}) is applied at the container network interface level. The \texttt{netem} discipline allows precise injection of packet delay, jitter, duplication, and loss. By combining deterministic and probabilistic impairments, \texttt{tc} enables experiments that replicate typical Wi-Fi multicast behavior, such as burst losses and variable latency, without requiring specialized hardware. Different impairment profiles can be applied per container to simulate heterogeneous client conditions.

\quad The evaluation was conducted inside a containerized environment designed for reproducibility and scalability, where the streaming server, Restreamer, multiple client replicas, and the monitoring stack each ran inside Docker containers connected to a shared bridge network \textbf{\Cref{fig:deployment}}, deployed on a \textbf{Razer Blade 15 Advanced Model (Mid 2021)} equipped with an Intel i7-11800H CPU (16 threads, up to 4.6,GHz), an NVIDIA RTX 3070 Mobile GPU, and 64GB of RAM, running Manjaro Linux with kernel version 6.6.99.

The roles of these components within the environment can be described as follows:

\begin{itemize}
	\item \textbf{Restreamer} ingested a live video source and re-encoded it into a format suitable for multicast delivery. This ensured a consistent input stream across experiments and isolated results from variability in video input.  
	
	\begin{figure}[H]
		\centering
		\includegraphics[width=0.95\textwidth]{Evaluation/restreamer.png}
		\caption{Restreamer interface providing the test video source for the evaluation.}
		\label{fig:restreamer}
	\end{figure}
	
	\item \textbf{tcgui} configured packet loss on the host-side \texttt{vethXXX} interfaces of the client containers. A Bash script automated the process by scanning for containers with the prefix \texttt{iris-client-*}, mapping each client’s \texttt{eth0} to its paired veth device, assigning a random packet loss rate, and posting the configuration to the \texttt{tcgui} HTTP API. This ensured that every client container experienced a reproducible yet randomized loss pattern at its ingress interface. Figure~\ref{fig:tcgui} illustrates the \texttt{tcgui} interface that applied these rules.
	
	
	\begin{figure}[H]
		\centering
		\includegraphics[width=0.80\textwidth]{Evaluation/tcgui.png}
		\caption{tcgui interface for configuring delay, jitter, and packet loss on client veth interfaces.}
		\label{fig:tcgui}
	\end{figure}
	
	
	\item \textbf{Prometheus} operated by periodically scraping data from an exporter embedded in the streaming server, storing the collected time series in its database for retrieval and analysis.
	
	\item \textbf{Grafana} connected to Prometheus and provided interactive dashboards to visualize these server-side metrics in real time and to archive them for later analysis. Dashboards tracked bandwidth usage, retransmission activity, and playback stability across all experiments.  
\end{itemize}



By combining Restreamer for video input, the \texttt{tc}+tcgui mechanism for applying randomized loss at the client interfaces, and the Prometheus--Grafana stack for server-side monitoring, the testbed provided a controlled and fully observable environment for reproducible experiments.


\subsection{Adaptive Redundancy and Reinforcement Learning}

Reinforcement learning with retransmissions disabled selected high redundancy, averaging \texttt{fec\_row = 4.2} and \texttt{fec\_col = 5.7}. This raised sender bandwidth to \textbf{5.49 Mbit/s} with \textbf{57\% overhead}, yet packet loss remained \textbf{2.8\%} and deadline misses increased to \textbf{16.4}.

\subsection{Retransmission Scheduler Efficiency}

With retransmissions enabled and no FEC, the server transmitted \textbf{4.82 Mbit/s}, of which \textbf{2.14 Mbit/s} were retransmissions. Loss fell to \textbf{1.85\%}, and deadline misses to \textbf{3.96}, the best performance among all runs.

With fixed 2$\times$2 FEC and retransmissions, retransmissions consumed \textbf{7.09 Mbit/s}, pushing server egress to \textbf{10.73 Mbit/s}, while loss worsened to \textbf{6.4\%} and deadline misses to \textbf{19.3}.

With RL-driven FEC and retransmissions, retransmissions dropped to \textbf{4.41 Mbit/s} and server egress to \textbf{7.97 Mbit/s}, yielding \textbf{3.9\% loss} and \textbf{11.4 deadline misses}.

\subsection{Peer-Assisted Mesh Recovery and Android Offloading}

Preliminary Android experiments confirmed correct operation on mobile hardware. End-to-end latency remained under \textbf{150 ms}, and CPU load was reduced by \textbf{12\%} compared to infrastructure-only recovery. While not all mesh networking results were captured in the workbook, these results validate the feasibility of client-assisted retransmissions through Wi-Fi Aware.

\section{Discussion}

Three insights emerge from the data. First, static FEC increased overhead without improving reliability, often worsening playback continuity. Second, retransmissions alone provided the best trade-off, reducing packet loss to below 2\% with moderate bandwidth. Third, reinforcement learning improved efficiency compared to fixed FEC when retransmissions were enabled, but it did not outperform the retransmissions-only case.  

Unicast dominated retransmission traffic, with multicast contributing less than 17\%, suggesting that further tuning of coding and multicast selection thresholds could yield stronger gains.

\section{Experimental setup and methodology}
\label{sec:methodology}
%% ----------------------------------------------------------------------------------------------------------%%

\quad Each experiment begins by deploying a single server container streaming a fixed-bitrate video source and a configurable number of client containers. The clients join the session, authenticate, and begin receiving the multicast stream with retransmissions enabled. For every test scenario, baseline runs without impairment are first executed to establish reference values for throughput, packet loss, and latency. Afterward, controlled impairments are introduced using \texttt{tc}, with parameters adjusted to represent realistic ranges of wireless behavior.

\quad The experiments are repeated multiple times under identical configurations to reduce variability and ensure statistical validity. Collected metrics include total bandwidth usage at the server, per-client recovery rate, average retransmission latency, reinforcement learning adaptation time, and the overall playback continuity as perceived at the client. These values are aggregated through Prometheus and visualized in Grafana, from which average, minimum, and maximum results are derived.

\quad Test scenarios are grouped according to whether edge-cloud offloading and mesh retransmissions are enabled, allowing a direct comparison between purely infrastructure-based delivery and cooperative client recovery.

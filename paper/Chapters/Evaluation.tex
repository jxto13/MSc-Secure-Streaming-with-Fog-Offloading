\chapter{Evaluation}
\label{Evaluation}
%

\quad This chapter evaluates the proposed livestreaming framework under controlled and realistic network conditions. The objective is to collect quantitative data that demonstrates how the architecture performs, extending the mechanisms introduced in \textbf{\Cref{Design and Implementation}} into practice. To achieve this, \textbf{\Cref{sec:evaluation environment}} first describes the experimental setup, including hardware platforms, containerized network configurations, and monitoring tools. \textbf{\Cref{sec:simulated results}} presents results from the simulated scenarios, highlighting the effects of retransmission, forward error correction, and reinforcement learning. \textbf{\Cref{sec:deployment results}} reports findings from real-world tests using the \textbf{\nameref{sec:android frontend}}, focusing on the feasibility of fog offloading. Finally, \textbf{\Cref{sec:discussion}} analyzes the outcomes across both environments and relates them to the system’s design goals.

\section{Evaluation Environment}
\label{sec:evaluation environment}

\quad The evaluation was conducted in a Docker-based containerized environment designed for reproducibility and scalability, where the \nameref{sec:streaming server}, Restreamer, multiple client replicas, and the monitoring stack each ran inside containers connected to a shared bridge network \textbf{\Cref{fig:deployment}}. The system was deployed on a \textbf{Razer Blade 15 Advanced Model (Mid 2021)} equipped with an Intel i7-11800H CPU (16 threads, up to 4.6\,GHz), an NVIDIA RTX 3070 Mobile GPU, 64GB of RAM, and running Manjaro Linux with kernel version 6.6.99, because of limited physical equipment, part of the evaluation relies on simulated tests that reproduce large-scale conditions, while the remainder consists of a real-world experiment using the Android implementation from \textbf{\Cref{sec:android frontend}} to confirm the feasibility of client offloading in practice.

\begin{figure}[H]
	\centering
	\includegraphics[width=0.95\textwidth]{Evaluation/system.png}
	\caption{Containerized deployment of server, clients, and monitoring stack.}
	\label{fig:deployment}
\end{figure}

The roles of these components within the environment can be described as follows:

\begin{itemize}
	\item \textbf{Restreamer} \cite{restreamer} ingested a live video source and re-encoded it into a format suitable for multicast delivery, this ensured a consistent input stream across experiments and isolated results from variability in video input, as shown in \Cref{fig:restreamer}.  
	
	\begin{figure}[H]
		\centering
		\includegraphics[width=0.95\textwidth]{Evaluation/restreamer.png}
		\caption{Restreamer interface providing the test video source for the evaluation.}
		\label{fig:restreamer}
	\end{figure}
	
	\item \textbf{tcgui} \cite{tcgui} configured packet loss on the host-side \texttt{vethXXX} interfaces of the client containers. A Bash script automated this by scanning for containers with the prefix \texttt{iris-client-*}, mapping each client’s \texttt{eth0} to its paired veth device, assigning a random packet loss rate, and posting the configuration to the \texttt{tcgui} HTTP API, this ensured that every client container experienced a reproducible but randomized loss pattern at its ingress interface. The graphical interface was used during development to validate configurations, while the script was employed during evaluation to guarantee consistency across runs, \Cref{fig:tcgui} illustrates the \texttt{tcgui} interface for manual rule application, while \Cref{fig:random loss script} presents the automation script.
	
	
	\begin{figure}[H]
		\centering
		\includegraphics[width=0.80\textwidth]{Evaluation/tcgui.png}
		\caption{tcgui interface for configuring delay, jitter, and packet loss on client veth interfaces.}
		\label{fig:tcgui}
	\end{figure}
	
	\item \textbf{Prometheus} \cite{prometheus} operated by periodically scraping data from an exporter embedded in the streaming server, storing the collected time series in its database for retrieval and analysis.
	
	\item \textbf{Grafana}~\cite{grafana} connected to Prometheus and provided interactive dashboards to visualize these server-side metrics in real time and to archive them for later analysis. Dashboards tracked bandwidth usage, retransmission activity, and playback stability across all experiments, as illustrated in \Cref{fig:grafana dashboard}.

\end{itemize}

\section{Simulated Results}
\label{sec:simulated results}

\quad To ensure fair comparison across experiments, all scenarios employed a fixed \(10 \times 10\) data matrix configuration, a \textbf{\nameref{sec:streaming server}} configuration example is shown in \textbf{\Cref{fig:server config}}.  


\subsection{Simulated Baseline}

\quad The baseline trace shows a sender rate of 2661 kbps against a source rate of 2129 kbps, producing a stable 20.0\% overhead (\textbf{\Cref{fig:overhead}}). Average packet loss reaches 2.40\% across clients (\textbf{\Cref{fig:packet_loss}}), while missed deadlines total 19,580 (\textbf{\Cref{fig:missed_deadlines}}). Because no FEC was applied, the difference between sender and source rates results solely from protocol overhead introduced by metadata, signatures, and padding, indicating a steady channel with modest but consistent headroom.

\subsection{Impact of Forward Error Correction}

\quad With 1x1 FEC (\texttt{ret\_off-fec\_1x1-ai\_off}), the sender rate increases to 3012 kbps while the source rate remains 2140 kbps. Overhead rises to 34.5\% (\textbf{\Cref{fig:overhead}}), roughly 14\% above baseline. Packet loss decreases to 3.73\% (\textbf{\Cref{fig:packet_loss}}), while missed deadlines climb to 33,437 (\textbf{\Cref{fig:missed_deadlines}}).

\quad With stronger 2x2 FEC (\texttt{ret\_off-fec\_2x2-ai\_off}), sender rate grows to 3854 kbps, overhead reaches 44.7\% (\textbf{\Cref{fig:overhead}}), and packet loss is 3.65\% (\textbf{\Cref{fig:packet_loss}}). Missed deadlines fall slightly to 27,730 (\textbf{\Cref{fig:missed_deadlines}}). Compared to baseline, overhead expands by nearly 25\%, confirming that stronger coding consumes more bandwidth without significant reliability gains.  


\subsection{Retransmission Effects}

\quad Retransmission alone (\texttt{ret\_on-fec\_off-ai\_off}) keeps sender rates at 2675 kbps with overhead at 20.1\%. Packet loss improves to 1.85\% (\textbf{\Cref{fig:packet_loss}}), and missed deadlines fall to 9538 (\textbf{\Cref{fig:missed_deadlines}}), about half of the baseline. This shows that retransmission improve delivery withou increasing overhead.  

\quad When retransmission combines with strong FEC (\texttt{ret\_on-fec\_2x2-ai\_off}), sender rate and overhead resemble the 2x2 FEC case (\textbf{\Cref{fig:overhead}}), but packet loss increases to 6.44\% (\textbf{\Cref{fig:packet_loss}}) and missed deadlines surge to 42,377 (\textbf{\Cref{fig:missed_deadlines}}). Retransmission smooths the fluctuations but does not counteract the inefficiency of heavy coding.

\subsection{Reinforcement Learning Adaptation}

\quad In the \texttt{ret\_off-fec\_off-ai\_on} scenario, sender rate doubles to 5489 kbps while the source rate remains at 2125 kbps. Overhead escalates to 57.5\%, almost 40\% above baseline (\textbf{\Cref{fig:overhead}}). Packet loss rises slightly to 2.76\% (\textbf{\Cref{fig:packet_loss}}), and missed deadlines reach 30,166 (\textbf{\Cref{fig:missed_deadlines}}). The AI controller improves robustness but at the cost of excessive redundancy. Enabling retransmission with AI (\texttt{ret\_on-fec\_off-ai\_on}) produces comparable trends, showing that AI dominates protocol behavior regardless of retransmission.  

\section{Deployment Results}
\label{sec:deployment results}

\quad The deployment experiments complement the simulated scenarios by validating the framework under real operating conditions. All configurations follow the same composition summarized in \textbf{\Cref{tab:scenarios}}, and the data matrix remains fixed at \(10 \times 10\) to ensure comparability with the earlier tests. In contrast to the containerized environment, these results rely on the \textbf{\nameref{sec:android frontend}}, which provides a practical mobile client and enables testing of fog offloading mechanisms on real devices. The experiments were conducted using an Asus RT-AC3200 access point running firmware version 3.0.0.4.382.52651, and mobile clients were Google Pixel 7a devices running Android build AP2A.240605.024. The goal is to confirm that the mechanisms designed in \textbf{\Cref{sec:mesh networking}} also operate efficiently when executed in practice.

\subsection{Deployment Baseline}

\quad In the real-world baseline scenario (\texttt{RL\_baseline}), the sender rate averages 2696 kbps, the source rate 2143 kbps, and overhead remains low at 20.0\% (\textbf{\Cref{fig:overhead}}), while packet loss is minimized to 1.80\% (\textbf{\Cref{fig:packet_loss}}) and missed deadlines total 9464 (\textbf{\Cref{fig:missed_deadlines}}).

\subsection{Fog Offloading}

\quad With fog offloading (\texttt{RL\_ret\_on-fog\_on}), the sender rate holds at 2695 kbps, the source rate rises slightly to 2154 kbps, and overhead remains stable at 20.1\% (\textbf{\Cref{fig:overhead}}), packet loss increases marginally to 2.50\% (\textbf{\Cref{fig:packet_loss}}), but missed deadlines drop significant to 1915 (\textbf{\Cref{fig:missed_deadlines}}), showing that offloading improves playback continuity under real operating conditions.

\section{Discussion}
\label{sec:discussion}

\quad The results show that static FEC, while simple to deploy, delivered poor efficiency under the observed Wi-Fi loss patterns, moving from no FEC to 1x1 and then 2x2 product codes increased overhead from a protocol baseline of roughly 20\% to 34.5\% and 44.7\% respectively, (\textbf{\Cref{fig:overhead}}), and didnt reduce packet loss or deadline misses to competitive levels (\textbf{\Cref{fig:packet_loss}}, \textbf{\Cref{fig:missed_deadlines}}), this demonstrates that product codes still encounter deadlock configurations when bursts intersect row and column parities, making the added redundancy insufficient to improve delivery.

\quad Targeted recovery via retransmission, coordinated by the scheduler in \textbf{\Cref{sec:network scheduler framework}}, produced the most favorable simulated trade-off, keeping sender rate and overhead aligned with baseline (\textbf{\Cref{fig:overhead}}), retransmission cut average loss to 1.85\% and halved missed deadlines to 9538 (\textbf{\Cref{fig:packet_loss}}, \textbf{\Cref{fig:missed_deadlines}}). This outcome is consistent with a design that reacts to actual erasures instead of protecting every packet in advance, the multicast–unicast cycle selected actions from the live NC matrix and enforced per-client and aggregate budgets, which limited waste and focused bandwidth where it changed outcomes. The aggregate egress remained stable (\textbf{\Cref{fig:egress}}), confirming that the gain came from smarter allocation rather than higher send rate, however, retransmission traffic was dominated by unicast, with multicast contributing under one fifth of recovery, so there is headroom to increase coding gains by raising XOR parity opportunities or adjusting selection thresholds to favor beneficial overlaps.

\quad The learning-driven configuration in \textbf{\Cref{sec:reinforcement learning}} adapted aggressively but not efficiently, in the simulated \texttt{ret\_off-fec\_off-ai\_on} case, sender rate doubled and overhead rose to 57.5\% (\textbf{\Cref{fig:overhead}}) while packet-level reliability changed little and deadline misses remained high (\textbf{\Cref{fig:packet_loss}}, \textbf{\Cref{fig:missed_deadlines}}). Discretized loss bins and a reward that penalizes loss more than redundancy steered the policy toward sustained parity increases, which improved resilience on paper but paid for it with redundant traffic that did not convert into packet recovery. 

\quad The real-world baseline held the protocol overhead near 20\% with 1.80\% loss and 9464 missed deadlines, closely matching the simulated retransmission-only efficiency point (\textbf{\Cref{fig:overhead}}, \textbf{\Cref{fig:packet_loss}}, \textbf{\Cref{fig:missed_deadlines}}). Enabling fog offloading kept overhead stable at 20.1\% and sender egress unchanged (\textbf{\Cref{fig:overhead}}, \textbf{\Cref{fig:egress}}) yet dropped missed deadlines to 1915, a large reduction despite a modest increase in raw loss to 2.50\% (\textbf{\Cref{fig:packet_loss}}, \textbf{\Cref{fig:missed_deadlines}}). This pattern indicates that mesh-assisted recovery shortened the path to missing packets enough to meet playback deadlines even when link losses persisted, which is exactly the role anticipated in \textbf{\nameref{sec:mobile edge cloud offloading}}. Because server overhead measures only the ratio between source and transmitted payloads, the stability of \textbf{\Cref{fig:overhead}} shows that offloading shifted recovery work to nearby devices instead of pushing more redundancy through the access point.

\quad Taken together, the evidence supports three conclusions. Static FEC proved ineffective under these conditions because constant redundancy and matrix latency failed to translate bandwidth into timely delivery. In contrast, the scheduler’s retransmission loop achieved the best efficiency by keeping overhead at baseline levels while reducing deadline misses through targeted recovery with budget controls. Fog offloading further strengthened the system by adding a low-latency recovery path, preserving server-side efficiency while sharply reducing deadline failures. Overall, the results indicate a clear operating point for dense Wi-Fi deployments: retransmission should be preferred over static FEC, coding should be applied opportunistically when overlap justifies the added cost, and fog offloading should be used to recover time-critical packets locally when infrastructure links cannot keep pace.
